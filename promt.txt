Contexto del proyecto
Estamos construyendo un marketplace de dos caras que conecta complejos deportivos con jugadores que quieren alquilar canchas de fútbol y otros deportes. El mercado objetivo es Perú y Latinoamérica. La moneda es el Sol peruano (PEN). Todo el código del backend va en inglés. Toda comunicación conmigo va en español.
El stack obligatorio es el siguiente. No puedes proponer cambios sin antes presentarme un ADR y esperar mi aprobación:

Backend: Laravel 11 con PHP 8.2, arquitectura hexagonal estricta
Frontend: React con TypeScript y Tailwind
Base de datos: MySQL 8
Cache y colas: Redis
El sistema corre directamente en Windows 11 sin Docker. El usuario tiene instalado PHP 8.2, Composer 2.9, Node.js 24 y MySQL. No tiene Redis todavía.

La pasarela de pagos está excluida del alcance por ahora. No la implementes, no la menciones como bloqueante y no dejes código que dependa de ella para que el resto funcione.

Los cuatro actores del sistema
El sistema tiene cuatro tipos de usuario con roles completamente separados. Ningún actor puede ver ni hacer lo que corresponde a otro:
El Usuario es el jugador que busca canchas, hace reservas y paga un anticipo digital. Accede desde la web o móvil.
El Partner es el dueño del complejo deportivo. Configura sus canchas, horarios y precios, gestiona su staff y ve la analítica de su negocio. Accede desde un dashboard web.
El Staff es el empleado que trabaja en el complejo. Abre y cierra turnos, escanea QR de los jugadores al llegar y registra reservas presenciales. Accede desde una PWA optimizada para móvil.
El Admin es el administrador de la plataforma. Aprueba Partners, resuelve disputas y configura las reglas globales. Accede desde un backoffice interno.

Reglas de arquitectura que nunca puedes violar
La arquitectura es hexagonal con tres capas. El Dominio contiene las entidades, value objects, eventos y las interfaces de los puertos. No importa nada de Laravel. La capa de Aplicación orquesta los casos de uso y llama a los puertos por sus interfaces. La capa de Infraestructura implementa los puertos y expone la API HTTP. Un archivo en la capa de Dominio que tenga un use Illuminate\... es un error grave que debes corregir antes de continuar.
Sobre la base de datos: todos los montos son DECIMAL(10,2) sin excepción. Todos los timestamps son UTC con tipo dateTime. Cada migración tiene su método down() funcional. Las búsquedas geográficas usan índices SPATIAL de MySQL, nunca cálculos en PHP. El campo de ubicación de los venues usa el tipo POINT con SRID 4326.
Sobre la concurrencia en reservas: cuando un usuario intenta reservar un slot, el sistema debe usar simultáneamente un lock distribuido en Redis con TTL de 600 segundos y una verificación optimista en MySQL con la columna version. Si cualquiera de los dos mecanismos falla, la operación se rechaza con error 409. Esto nunca es opcional.
Sobre los webhooks de pago: aunque la pasarela está excluida del alcance actual, la arquitectura debe dejar el espacio preparado para recibirlos. La confirmación de una reserva como pagada nunca puede venir del frontend. Solo puede venir de un webhook firmado que llegue al backend.

Reglas de seguridad
Nunca escribas secretos, API keys, contraseñas ni URLs de producción en el código. Todo va en variables de entorno y en el archivo .env que nunca se commitea. El archivo .gitignore debe excluir .env desde el primer commit. Los tokens de autenticación tienen scope por rol. Los tokens del Staff expiran al cierre de su turno.

Reglas de calidad de código
PHP con declare(strict_types=1) en todos los archivos. PHPStan nivel 8. TypeScript en modo strict. No hay dd(), var_dump() ni console.log en código que se vaya a commitear. Los comentarios explican el por qué, no el qué.
